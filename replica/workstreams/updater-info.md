# About / Updates — app-info, auto-update

## Delivery status

Implemented a production native vertical slice, **not a shipment-ready release**. The parent still owns integrated Windows/Linux desktop builds, packaging, private publication and deployment. No running app was launched, restarted, closed, installed over, focused, or controlled. No Discord/account API was exercised and no GitHub token was extracted. No release was uploaded.

- `app-info`: Settings section **9 / About & Updates**, available in both native layouts (including local preview). Shows the **running** Harmony version, explicit build ID, compile-time full Git commit / dirty-development indication, target OS/architecture, upstream Yapfast 0.3.0, GPL-3.0-or-later and source attribution. Copy uses the existing native clipboard function and a compile-time allowlist, never environment dumps, account IDs, data paths or raw provider output.
- Independent Harmony package version **1.0.0** replaces the misleading upstream 0.3.0 identifier for the root desktop package only. `build.rs` stamps actual Git identity. `HARMONY_BUILD_ID=0` (default) is development; positive release build IDs require a clean committed tree. Each later release should increment SemVer and/or the explicit numeric build ID. Same SemVer/build ID with a different commit is rejected, never silently substituted.
- `auto-update`: real private-GitHub metadata/asset bridge via the optional **official installed `gh` CLI**, not an embedded PAT. Literal github.com API paths are pinned to `TimeShallHalt/harmony`; release-supplied URLs are validated, never executed/fetched as destinations. Token/debug/host overrides are removed from the child environment; stdin/stderr are closed/discarded. The CLI owns secure keyring auth/TLS/GitHub asset redirects. Missing CLI, missing/expired auth or offline auth checks, provider failure/rate limits, no newer/no published stable release, size/hash/platform failure, cancellation and concurrent checks have explicit outcomes.
- Startup checks are event-driven, at most once per persisted 24-hour interval, including failed attempts. No recurring poll/timer. Automatic download is opt-in and only stages a verified update. Manual check/download remain available. Preview does not automatically check or modify staging/install state.
- Actual downloads stream through a size cap, are rehashed with SHA-256, validate PE/ELF AppImage target architecture, and publish an owned staging journal only after verification. No ZIP/TAR/extractor exists, so archive traversal/link entries cannot be interpreted. Filenames, platform, repo, tag, manifest schema, full commit, asset ID/URL/name/size and digest are checked.
- Staging is sibling `.harmony-updates/txn-*`, protected by an exclusive OS file lock and ownership/no-untrusted-write checks (Linux uid/mode, Windows owner/DACL). Linux uses held-directory `openat`, no-follow `O_PATH` regular-inode checks and genuine procfs descriptor reopening; Windows uses `NtCreateFile` RootDirectory + OBJ_DONT_REPARSE and handle-relative rename/delete. Symlinks, junctions, hardlinked files, devices/FIFOs, unsafe names, ADS and Windows network/device paths fail closed.
- **Install on full exit** explicitly arms a single staged update. Disarm/discard are synchronous small local transactions so full quit cannot overtake a queued disarm. Closing to tray and renderer restarts never activate. After a natural full quit, a copy of the existing verified binary acts as the native helper, waits on the parent process OS event (no termination/pid polling), verifies again, creates and verifies rollback, atomically replaces the launch target, then reads it back. It never relaunches Harmony. Account/session data is not migrated or overwritten. Failure retains/restores the previous target and journal/rollback; interrupted post-publication journals can be completed. A busy update on full quit is canceled/deferred, never forced into installation.

## Publishable release contract

No separate helper artifact is needed: the installed Harmony executable/AppImage contains the early `--harmony-update-helper` entry point, before UI/runtime/TLS. A copied old image performs the transaction; downloaded code is not run by the updater.

1. Commit integration and select a positive monotonically increasing `HARMONY_BUILD_ID` before the parent's normal supported release build on each platform. Dirty trees cannot claim a release ID. Each build writes `OUT_DIR/harmony-build-info.json`; `--harmony-build-info` is also an account-free metadata entry point (not exercised against a live app here).
2. Sign/verify and test the actual final binaries **before** assembling the manifest. Build-stamp consistency is checked, but the publisher must establish that the supplied final binary really corresponds to that stamp/source. Header checks/checksums are not an authenticity or malware certification.
3. Offline helper (paths below are example build-output paths, not existing delivered artifacts):

   ```sh
   python scripts/harmony-release-manifest.py \
     --version 1.0.0 --build-id 1 --commit FULL_LOWERCASE_GIT_SHA \
     --artifact windows-x86_64=dist/windows/yapfast.exe \
     --build-info windows-x86_64=dist/windows/harmony-build-info.json \
     --artifact linux-x86_64=dist/linux/Harmony.AppImage \
     --build-info linux-x86_64=dist/linux/harmony-build-info.json \
     --output-dir dist/harmony-v1.0.0-b1
   ```

   Requires an empty owned output directory, canonical stable SemVer, clean matching build metadata for every artifact, and bounded raw PE / type-2 AppImage inputs. Produces `harmony-update-v1.json`, `Harmony-1.0.0-windows-x86_64.exe`, `Harmony-1.0.0-linux-x86_64.AppImage`, real `SHA256SUMS.txt`, `LICENSE.txt`, and `SOURCE.txt`. Artifacts precede the manifest; failures remove only newly created output. Optional aarch64 manifest formats exist but have **not** been built/tested here.
4. Parent alone creates a **published, non-draft, non-prerelease** private release tagged exactly `harmony-v1.0.0-b1`, targeting the matching commit, and uploads those files. Keep complete source/third-party notices available to recipients. Actions remain disabled. Do not use an installer ZIP or stock Yapfast release as the portable update payload. The provider bounds its listing to the newest 100 releases, chooses the greatest stable Harmony tag, then requires its matching platform asset; a missing platform is explicit rather than a silent fallback.

## Remaining limits / parent gates

- No real private release exists yet according to the dispatch context. No live gh auth/API request was made as a test. Parent must publish/verify a real release and test the actual official CLI/account bridge; the app must honestly report no release/auth/offline rather than claim an update.
- No independent manifest signing/key rotation, Authenticode verification, antivirus pipeline, transactional installer elevation or package-manager updates are implemented. Trust is the authorized repository + installed official gh + SHA-256. Signing must happen before hashes are assembled. The UI explicitly says so.
- Windows portable and Linux AppImage paths require a writable user/admin-owned installation. Linux requires procfs, pidfd (Linux 5.3+) and supported rename operations; other layouts/kernels fail explicitly. Native standalone ELF helper behavior passed on Linux, but **packaged AppImage/FUSE bootstrap and the full Linux desktop have not been exercised**. Parent must verify those before calling Linux updater delivery ready.
- These checks do not build/relaunch/install the complete desktop app, measure full idle performance, exercise real physical input, or validate the user's active call. Preserve the baseline unrelated emoji test failure until its owner supplies the fix. Rollback/journals are deliberately retained; interrupted `Applying` state requires review/recovery instead of a destructive Discard button. No automatic rollback cleanup or power-loss/filesystem certification is claimed.

Shared-file edits are intentionally small: version/lock/build stamp hook, one desktop module, one adapter field and layout preference field, callback/startup/full-exit hooks, and Settings section 9 registrations. Most implementation lives in `src/harmony_update/`, `src/ui/updater_info*`, `ui/about_updates.slint`, `scripts/harmony*`, and updater-specific testing files. No shared feature matrix or top-level development docs were edited.
