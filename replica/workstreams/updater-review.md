## Security concerns

1. **P1: inheritable Windows child ACLs.** `src/harmony_update/windows_fs.rs:258` skips inherit-only ACEs, while `open()` at line79 creates entries with a null security descriptor. An untrusted SID's object-inherit/inherit-only write ACE can pass directory checks yet grant write to payload, plan and helper files. File opens check type/link count, not file ACL. Modifying payload plus persisted expected hash/authorization defeats the assumed staging boundary. Reject unsafe inheritance or create protected DACLs and validate actual files. A broad Everyone-directory-write test is insufficient; test object-inherit/inherit-only grants on actual child objects.
2. **P1: helper is not bound to the running image.** `controller.rs:193-206` supplies only a pathname and trusts Linux APPIMAGE. `transaction.rs:195` hashes whatever occupies that path; `spawn_helper():419-428` copies/executes bytes matching that same path-derived hash. A replaced installation or unrelated APPIMAGE can therefore supply another executable. Establish running-image identity independently, pin it through helper copy/handoff and fail closed when unavailable. Another hash of the same mutable path is not independent proof.
